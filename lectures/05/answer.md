- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行した結果、上位5件として第2回（`lec02-main`）の **p.52、p.51、p.60、p.47、p.61** が取得された。
  - **検索結果1（PDF p.52「LoRA と QLoRA ：大きなモデルも GPU 1 台で調整できる」）：** 「元の重みは固定し、小さな『差分』だけを学習する（LoRA）。さらに元の重みを 4bit に圧縮する（QLoRA）」という質問への直接的な答えと、行列 $A \cdot B$ の図解・メモリの目安が記載されていることを確認できた。
  - **検索結果2（PDF p.51「PEFT ：モデル全体ではなく、一部だけを学習する」）：** Full Fine-Tuning・LoRA・QLoRAの比較図や、PEFTの主な手法の位置づけが補足情報として記載されていることを確認できた。

  - **ベクトル検索：** `search_materials({'query': 'LoRA QLoRA 固定 学習 第2回'})` を **1回** 呼び出し（モデル応答は2回）。上位ヒットの `lec02-main-p052` 等を取得して回答。

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - **取得した情報が足りなかった例：** 今回の質問においては、どの検索方式でも核心となる p.52（および p.51）を取得できたため、情報不足による誤答は起きなかった。ただし Tree 探索では、モデルが p.52 のみを開いて完了したため、p.51 に記載されている PEFT 全体の比較文脈までは取得しなかった。

- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式：** **ベクトル検索**（または複数ページ横断が必要な質問が多い場合は **Graph**）。
  - **理由：** 講義資料の特定の用語や仕組みを尋ねる用途では、ベクトル検索が最も少ない入力トークン数（3,037 tokens）と最安の推定コスト（$0.001461）で、全文投入やTree・Graphと同等の正確な回答と根拠ページ（p.51, p.52）を返せたため。全文投入は1回の応答で済むものの入力トークン数が約38倍・コストが約24倍かかり、Treeは階層をたどるため応答回数（5回）と時間（5.82秒）が増える。
  - **比較条件の限界：** 全文投入は「全9資料・438ページ」を対象としているのに対し、ベクトル検索・Tree・Graphは「第1〜3回の本講義214ページ」のみを対象としており、検索母集団の広さが揃っていない。また、今回の検証は単一トピック（1〜2ページで完結する質問）1問のみの結果であるため、複数章にまたがる比較質問や資料に存在しない質問を含めた評価を行わなければ方式全体の優劣は断定できない。
- 気づき・疑問：
  - **全文投入時と検索ツール使用時の振る舞い（トーン）の違い：** 全文投入では「具体的な答えをそのままお伝えすることはできませんが、考え方のヒントを以下に示します」と学習支援ボットらしいヒント形式の応答になったのに対し、検索ツールを使った3方式（ベクトル検索・Tree・Graph）では直接的な解説形式で回答が生成された。コンテキスト量（22万文字超か数千トークンか）やツール利用の有無によって、システムプロンプトの指示への従い方や応答スタイルが変化する点が興味深い。
  - **Tree探索のコスト構造と網羅性のトレードオフ：** Tree探索はベクトルDBや埋め込みが不要で目次の構造通りに人間らしくたどれるメリットがある一方、階層を1段ずつ降りるたびにそれまでの会話履歴と目次一覧が入力トークンとして積み上がるため、結果的にベクトル検索の約3倍の入力トークン（9,214 tokens）と約2.4倍のコストがかかっていた。目次がさらに深い資料では、探索ステップ数とトークン膨張をどう抑えるかが課題になると感じた。

  - **改善・確認できた点：**
    - `RAG_TOP_K` を `2` に絞ったことで、1回あたりの検索で混入する周辺ページ（p.13, p.38 など）が減り、本当に核心となるページ（p.39, p.40, p.65）に絞った引用になった。

  - **残る制約・悪化した点：**
    - 「検索件数を減らせば入力トークン数とコストが下がる」と予想していたが、複数ページにまたがる質問では1回で取りきれずにツール呼び出しが1回→2回に増えたため、会話履歴やツール定義の往復分が加算され、**結果的に入力トークン数（2,500 → 3,432 tokens）・時間（3.94秒 → 7.03秒）・コスト（$0.001938 → $0.002237）のすべてが増加**した。

- 気づき・疑問：
  - **「1回あたりの検索件数（`TOP_K`）削減＝コスト削減」とは限らないという逆説：** エージェント型RAGでは、モデルが情報不足を検知して追加のツール呼び出し（再検索）を行うため、`TOP_K` を絞りすぎると「検索の往復回数」が増えてかえって総入力トークン数とレイテンシが悪化する現象が起きることを実測で確認できた。複数トピックにまたがる質問が多い用途では、1回の検索で関連ページをまとめて拾える程度の件数（`TOP_K = 5` 前後）を確保した方が、トータルのコストと速度の効率が良い。
  - **疑問点：** 今回は質問文が2つの論点（「コンパクションとセッションまたぎの違い」「日々のメモと長期メモリ」）を明確に含んでいたためモデルが2回目の検索へ動けたが、論点が暗黙的な質問の場合、`TOP_K = 2` だと情報不足に気づかず不完全なまま回答を打ち切ってしまうリスクがどの程度あるかと思った。
